# App Router Reference

## Location
- **Correct**: `/src/app`
- **Wrong**: `/app`

## Route Groups & Page Structure

### Folder Organization

```
src/app/
├── (app)/              # App service pages (AppLayout)
│   ├── page.tsx        # Home page
│   ├── layout.tsx      # AppLayout (user auth + App UI)
│   └── {route}/        # Additional pages
│
├── (admin)/            # Admin service (separate service)
│   └── admin/
│       ├── layout.tsx          # AdminLayout (admin auth + Admin UI)
│       ├── (dashboard)/page.tsx # Dashboard
│       ├── (dashboard)/account/page.tsx # Password change (login required)
│       ├── login/page.tsx       # Admin login
│
└── layout.tsx          # Root layout (global: StateProvider, OverlayProvider, Toaster)
```

### Roles by Route Group

**`(app)/` - App service pages**
- Main application pages
- Provides user authentication + App UI via AppLayout
- Page components: import from `@/services/app/page/`

**`(admin)/admin/` - Admin service pages (internal route)**
- Admin pages (completely separate service)
- Provides admin authentication + Admin UI via AdminLayout
- Page components: import from `@/services/admin/page/`
- Keep this internal `/admin` directory stable. User-facing links use
  `adminRoutes` from `@/lib/admin-routes`; `src/proxy.ts` maps the project's
  public admin path to this directory.

### NEVER create `src/app/page.tsx`
- **WRONG**: `src/app/page.tsx` (BUILD ERROR!)
- **CORRECT**: `src/app/(app)/page.tsx`

### Layout Hierarchy

1. **Root Layout** (`src/app/layout.tsx`)
   - Global: StateProvider, OverlayProvider, Toaster, ReactGrab, SandboxBridge
   - No user authentication (handled in each service layout)
   - import `@/lib/layout`

2. **Service Layouts**
   - `src/app/(app)/layout.tsx` → `@/services/app/page/layout` (null Suspense → await basic user → client hydration)
   - `src/app/(admin)/admin/layout.tsx` → `@/services/admin/page/layout` (null Suspense → await basic admin user; protected routes keep a server auth guard)

## Rules

### Imports
- Page components: import from `@/services/{service}/page/`
- Layouts: import from each service's `page/layout`
- Server data fetching can be done directly in the app router when needed

### Next.js 16
- `params` is a Promise: `const { id } = await params` in `generateMetadata` and
  route handlers. Never await it in a detail page body (Data routes below).
- Don't use `'use client'` on app-router files, except Next.js-required error
  boundaries (`error.tsx` and `global-error.tsx`). Put reusable client UI in
  `src/lib/` and keep the route file as a thin boundary.
- Mark a Server Component `async` only when it actually awaits data. Keep
  app-router wrappers synchronous; the service auth layout is async because
  it awaits `getMe()` below that wrapper's `<Suspense fallback={null}>`.
- Keep this auth boundary before auth setup too. `TODO(auth-setup)` comments
  mark the mock/session wiring that the skill must replace. The client layout
  calls `useUser.hydrate({ me: { data: initialUser } })` before children render.
- Await only Better Auth session/basic user data here; separate member/profile
  tables load lazily through their own queries. Do not add an auth skeleton.

### Data routes (lists and details)
Route files render only a Suspense boundary (plus the static shell for lists).
The page component reads its data with `.suspend(arg)`, which SSRs in the same
request (SEO) and reuses the streamed result on the client — no `initialData`
props, no route adapters. See `src/services/page.ai.md` (Lists, Detail Pages).

```tsx
// detail — static body; the client view reads the id with useParams and makes one .suspend(id)
import type { Metadata } from 'next'
import { connection } from 'next/server'

export async function generateMetadata({ params }: { params: Promise<{ id: string }> }): Promise<Metadata> {
  const { id } = await params
  const post = await api.post.findById(id).catch(() => null)                   // the only server read
  if (!post) return { title: 'Post', robots: { index: false, follow: false } } // noindex for a missing item
  return { title: post.title, description: post.excerpt }
}

export default function Page() {
  return (
    <>
      <Suspense fallback={<PostDetailSkeleton />}>
        <PostDetailRoute />                 {/* 'use client' in the page layer: useParams → <PostDetail postId={id} /> */}
      </Suspense>
      <Suspense><Connection /></Suspense>   {/* dynamic marker: metadata is request-time, the body stays static */}
    </>
  )
}

async function Connection() {
  await connection()
  return null
}

// list — static shell outside, the list in its own boundary
export default function Page() {
  return (
    <Posts>
      <Suspense fallback={<PostListSkeleton />}>
        <PostList />
      </Suspense>
    </Posts>
  )
}
```

- Suspense fallbacks are skeletons, never `null` (only the service auth wrapper keeps `null`).
- A detail body never awaits `params` or data: that makes it a dynamic hole, and every soft
  navigation then waits for the server before the body paints. `generateMetadata` streams and
  does not block. In-app navigation from a list paints the model's `seed` at once; not-found is
  the view's `data === null`; JSON-LD renders from the query data.
