# Repository

## Role

The single gateway for DB access. The api layer must not call the DB directly. It must always go through the repository.

## Rules

- `import 'server-only'` is required in every file
- Group entities by Aggregate Root (e.g., include comment inside post.ts)
- Define and export types within each entity file
- Default timestamps: `createdAt`, `updatedAt`, `deletedAt`
- **ID generation uses `uuid()` (UUID v7)** — use the helper from `id.ts`. `Math.random()`, `Date.now().toString()`, and hardcoding are forbidden
- Faithfully expose the raw table values (frontend-friendly conversions belong in the api layer)
- Excluding soft-deleted records (`deletedAt != null`) is the default when querying
- Deletion is always a soft delete (update `deletedAt`)
- When adding a query, define a matching index in the Drizzle schema (`src/server/db/schema.ts`) on the columns it filters, joins, or sorts by

## ID Generation

Inside `create()`, the new record's `id` must always be generated via `uuid()`. UUID v7 is time-ordered, so it is safe to use as a DB PK.

```ts
import 'server-only'
import { uuid } from './id'

export async function create(data: { title: string }): Promise<Post> {
  const now = new Date()
  const post: Post = {
    id: uuid(),
    title: data.title,
    createdAt: now,
    updatedAt: now,
    deletedAt: null,
  }
  posts.push(post)
  return post
}
```

> Seeds pre-populated in mock `_data/` may keep readable strings (e.g., `mock-user-001`). Only use `uuid()` in runtime `create()`.

## CRUD Naming

| Function | Description |
|------|------|
| `findAll(filter, pageable: PageRequest): Pageable<T>` | List query. Pagination is required as the second argument |
| `findById(id): T` | Single record lookup |
| `create(data): T` | Create |
| `update(id, data): T` | Update |
| `delete(id): void` | soft delete |

## Shared Types

Defined in `repository/types.ts`:

```typescript
export type PageRequest = {
  page: number
  limit: number
}

export type Pageable<T> = {
  items: T[]
  total: number
  page: number
  limit: number
  totalPages: number
}
```

## Image Columns

Use one consistent image-field shape.

- Standard: **`ImageAsset { url, width, height, thumb? }`** (`@/lib/image`, installed by Comwit MCP `setup_storage`).
- Store **`JSON.stringify(ImageAsset)`** in an `image text` column; use JSON-encoded `ImageAsset[]` for multiple images.
- Expose the raw string unchanged. **Parse it with `JSON.parse` in the API layer**, which owns frontend-friendly transformations (see Rules).
- Save `width`/`height` directly from `resizeImage()` during upload to prevent CLS when displaying.
- See "Image Uploads" in `services/page.ai.md` for the resize/upload flow.

## Structure

```
repository/
  .ai.md
  types.ts              ← Shared types such as Pageable, PageRequest
  schema.dbml           ← Optional entity relationship sketch; `src/server/db/schema.ts` is the source of truth
  _data/                ← mock data (server-only)
    {entity}.ts
  {entity}.ts           ← Entity CRUD (server-only)
```

## Work Order

1. **Design the entities first** (a `schema.dbml` sketch is optional) — then express them in `src/server/db/schema.ts`
2. Write `_data/{entity}.ts` — normalized mock data based on the dbml
3. Write `{entity}.ts` — implement CRUD, referencing `_data`

## schema.dbml

- When adding or changing entities, always update the dbml first
- Specify relationships (1:N, M:N, etc.)
- Tables that the auth skill will generate are noted in advance as comments

## Mock Data Rules (_data/)

- `import 'server-only'` is required
- **Normalization**: Store flat like tables. No duplication; reference by ID
- **Relationships**: Hold join keys. Include FK fields like `userId`, `postId`
- **Join on query**: In the repository, join across `_data` to retrieve (just like a real DB join)
- No hardcoded computed values — values such as `likeCount` must be calculated from the related `_data`

## When Migrating to a DB

When transitioning from mock to a real DB:
- Replace only the internal implementation of the repository: `_data` → Drizzle queries
- Keep the function signatures (interface) the same
- No changes needed in the api layer

## Connected course platform implementation

This project now uses the real Drizzle schema; old mock examples above are historical reference only.
All money and enrollment mutations use `atomic()` from `./atomic`. The Cloud HTTP transport does not support an interactive `db.transaction()` across requests. `atomic()` reads a shared revision, lets the callback read and stage SQL with `add()`, then commits the revision guard and SQL in one atomic batch. A failed guard retries from fresh reads; a failed statement rolls back the whole batch.

Never execute a write directly inside the planning callback, and never call Toss, Storage, or any external side effect there. Stage writes and audit entries with `add()`. Every money/enrollment writer must participate in the revision guard. The only exception is the lesson progress heartbeat (`enrollments.saveProgress`): it is an idempotent upsert in a plain `db.batch()` so frequent player saves never contend with the guard. Authentication uses Better Auth's adapter with interactive transactions disabled. Keep the DB client batch's explicit `immediate` mode and raw tuple mapping.

Order snapshots (course title, list price, discounts, total) are immutable. One order holds one course; refunds are full-amount and revoke the enrollment in the same batch. Coupons are held at order creation, consumed on payment approval and released on cancel/expiry. Provider operations use durable request keys and are reconciled after ambiguous responses. A browser redirect or an unverified webhook body cannot mark an order paid. Storybook fixtures are separate from operational repository data.
