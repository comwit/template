# Storybook: Page-Level Screen Review

Read `design-system/design.mdx` and this document before changing screen design.
The design guide is the maintained source for shared theme principles. Course page
stories are loaded from `src/stories/` by `.storybook/main.ts`; preserve that
configuration and its course API mocks when extending the preview.

Run `pnpm storybook` for the shared preview, normally on port 6006. Run
`pnpm storybook:build` for the static preview in `storybook-static/`.
Keep Storybook checks separate from service validation and production builds.
Unfinished or incompatible mocks must fail preview checks rather than change
service behavior. Service code must never import Storybook fixtures.

## Page stories

- Group by user type, page and state: `강의/{page}` and `어드민/{page}`. Keep
  default, empty, loading, error and permission states as exports of the same
  page story. Add only states the real implementation supports.
- Import real pages from `src/services/{service}/page/`. Do not duplicate page
  JSX or create alternate learner-screen implementations just for a preview.
- Use the real layouts where a page requires them. Headers, sidebars and navigation
  must match the product. Do not import async layouts or the root App Router layout.
- Set `nextjs.navigation.pathname` to the real path and use `adminRoutes` for admin
  pages. Use stable English story IDs when overriding generated IDs.
- Use the same story at mobile and desktop sizes; do not create separate user types
  for device widths. Existing primitive stories may exercise production components,
  but new screen work needs page stories with the real state/action flow.
- Review actual routing, session authorization and server integration separately in
  the application. Storybook does not prove those production boundaries work.

## Mock only the API boundary

```text
Real page + real layout → real state/query/action → public API mock
                                                   ✕ real server/repository/DB
```

- `src/stories/mocks/app-api` and `admin-api` mirror public API domains. The aliases
  in `.storybook/main.ts` replace public imports; an unmocked production API import
  must fail the preview build. Read `src/stories/mocks/.ai.md` before extending them.
- Match the real export, argument and response contracts with `import type` and
  `satisfies DomainAPI`. Never runtime-import real actions, repositories or a DB.
- Do not mock state hooks, queries, actions or page markup. Loading/error/empty
  states come from API responses, not direct edits to `isLoading`, `isError` or data.
- `PreviewState` remounts the real state provider per story and hydrates only the
  two basic session queries from fixed fixtures. This replaces the server-auth
  boundary for previews; business data still comes through API mocks.
- `runtime.ts` resets fixtures and overrides in `beforeEach`; `apiMock` parameters
  choose response modes, delays and illustrative data. Clone responses so reactive
  proxies and edited arrays never mutate the fixture store.
- Auth, payment SDK and upload boundaries have local mocks. Never call real auth,
  payment, storage or notification providers from Storybook.
- Use `play` with awaited assertions for user interactions and results. Do not use
  arbitrary sleeps. Keep stories and fixtures separate from operational data.

## Design and theme maintenance

- Read and update `design-system/design.mdx` before changing design direction.
  Keep the guide concise and user-facing; developer workflow belongs here. Do not
  create a separate competing design guide or a `/design` application route.
- Every visual element must support hierarchy, understanding, action, feedback or
  brand. Avoid habitual eyebrow/subtitle/helper stacks. Public sections should
  communicate one main message with a supporting visual.
- Actual tokens live in `src/app/globals.css`. Override palette, typography, radius,
  elevation and motion there; do not edit installed `comwit-tokens.css` to rebrand.
- Change the brand family together and keep success/warning/error/info independent.
  Check light/dark surfaces and text contrast at mobile and desktop sizes.
- Reuse semantic UI classes and the local Pretendard font. Promote repeated custom
  values into theme tokens; keep one-off layout values local.
- Existing design-system source specimens under this directory remain reference
  material. If adding them to the active course preview, wire their stories and MDX
  support deliberately and validate the combined preview.
- Update the affected page stories alongside screen changes, run service
  `pnpm validate` and preview `pnpm storybook:build`, and inspect the real states.
